## 1. 项目定位与产品边界

「知行AI」是独立的 AI 对话产品，与「知行AI学习版」和「知行计算器AI版」存在关联，但不是同一个前端页面。

目前已知的产品/入口关系：

- **知行AI**：独立的聊天产品，拥有自己的前端、后端配置和对话体验。
- **知行AI学习版**：面向学习场景的独立产品，已知访问入口为 `https://c.zhixing.us.ci/ai`（此前对话中提供；上线状态需复测）。
- **知行计算器AI版**：集成在计算器中的 AI 分析功能，应结合当前计算器页面与计算结果工作，而不是要求用户把页面内容重新输入聊天框。
- **统一管理后台**：用户要求将多个产品放在一个后台统一管理，而不是分别进入多个互不相关的管理系统；但各产品的配置、会话和权限边界仍需隔离。

重要边界：此前用户明确反对在普通计算器里额外添加账号登录。账号认证应只出现在确实需要认证的 AI 产品/功能中，不得擅自把普通计算器改成必须登录才能使用。

## 6. 统一后台与管理能力

用户提出的方向是：多个 AI 产品在同一个管理后台中统一管理，减少重复入口，同时让各产品设置相互隔离。

已知期望的后台功能包括：

- 统一的后台登录入口与移动端适配。
- 按产品切换管理范围，例如知行AI与学习产品；各自的提示词、模型、API 配置、使用统计和会话数据必须有清晰边界。
- 管理模型名称、上游 API 地址、默认模型与提示词。
- 从上游 API 获取模型列表，并能够实际选择模型。
- 检查 API 连通性、模型调用结果和错误详情。
- 在上游支持且权限允许的情况下查看余额/额度；若接口不支持，需明确显示“上游未提供/无法查询”，不能伪造余额。
- 查看 token 用量、请求次数、响应延迟、错误率等使用统计。
- 备份/恢复后台配置；导出内容应排除密钥明文。
- 对管理操作、配置变更和异常请求保留必要审计记录。
- 页面应以移动端为优先，使用清晰、简洁的布局，避免大量说明文字、狭窄栏位、竖排文字、控件错位和过大的模型选择区域。

后台登录/账号功能的具体规则必须以最新用户指令和实际实现为准。密码应由用户自行设置或通过安全流程初始化；不得把默认密码、密码哈希、会话令牌或密钥暴露在前端源码中。

## 7. 用户认证与访问限制（需区分产品）

此前用户要求为 AI 产品增加账号认证与后台账号管理，并提出以下规则：

- 可在后台管理已认证账号。
- 账号需要用户名；用户名由后台/账号管理流程设置，不能重复。
- 用户可以使用用户名和密码登录。
- 已认证账号不受普通 IP 对话频率限制（这是历史需求，最终实现仍需安全评估和确认）。
- 普通 IP 的历史限流要求：每个 IP 每 15 分钟最多 15 次对话请求。
- 多个产品的账号管理希望在统一后台里完成。

安全注意事项：

- 不能仅依赖前端判断是否登录或是否超限；必须在服务端验证身份并执行限流。
- 用户名唯一性必须由数据库约束或可靠的服务端逻辑保证。
- 密码应使用经过审查的密码哈希方案存储，不能明文保存。
- 会话 Cookie 应正确设置 Secure、HttpOnly、SameSite 等属性（视部署方式适用），并防止会话固定、CSRF 和暴力破解。
- IP 限流应考虑代理头可信边界，不能直接信任客户端自行提交的 IP。
- 对已认证用户免除某一类限流时，仍应保留合理的滥用防护、并发限制和成本保护。
- 不得将普通计算器本身改为强制登录。必须明确哪些 AI 页面需要认证、哪些普通工具无需认证。
- 最近对话中用户曾指出：账号登录窗口设计错位、旧登录窗口没有删除、普通账号管理页面无法登录，以及多个 AI 页面（知行AI、学习版、AI计算器）存在布局不一致。需要逐页验证并统一登录窗口，而不是只修改其中一个页面。

## 8. 前端交互与设计要求

用户长期反复强调以下体验要求：

- 移动端优先，尤其要兼容 Android 手机浏览器。
- 登录窗口在各 AI 页面中应保持一致，尺寸、间距、输入框、按钮、错误提示和关闭行为都应正常。
- 统一管理后台的页面应简洁、易读，避免说明文字堆积和文字竖排。
- 修复标题、导航、弹窗、模型选择框、最近对话列表等控件的错位与重复。
- 请求状态必须可靠：不要出现重复的回答、重复的会话或失败后残留的“正在思考”提示。
- 错误提示应有用、明确，并避免把内部密钥或敏感上游响应原样泄漏给访客。
- 数学公式应使用正确的数学排版；如支持 Markdown/LaTeX，应验证行内公式、块级公式、上下标、分式和长公式在手机屏幕上可读。
- 图片/文件输入能力是否属于知行AI当前版本，需要以仓库现有代码为准；历史需求曾包含图片识别、文件上传、相机/图片入口等，但不能据此断言所有入口当前都已实现。

## 9. 对话与模型功能目标

历史产品需求涉及：

- 普通 AI 连续对话与上下文跟进。
- 图片/题目识别等输入能力（需确认当前模型与前端实现支持情况）。

对于知行计算器AI版，历史要求尤其强调：AI 分析应自动携带当前页面、输入值、计算结果等上下文，按页面类型展示分析结果，而不是让用户复制粘贴；重要信息默认展示，次要内容可以折叠。此项属于计算器 AI 的产品要求，只有在共享组件确有需要时才应同步到知行AI。

## 10. 安全与隐私基线

所有后续开发均应遵循：

1. **绝不提交密钥**：上游 API Key、Cloudflare API Token、Supabase service-role key、数据库密码、管理员密码、JWT 签名密钥等只能存放在受控的服务端 Secret/环境变量或合适的密钥管理系统中。
2. **前后端分离**：浏览器不得直接携带上游私密 API Key 请求模型服务。
3. **最小权限**：管理 API、普通对话 API、账号 API、配置 API 和统计 API 应实施独立鉴权与权限检查。
4. **敏感信息脱敏**：日志不得保存完整密钥、密码、Cookie、Authorization 头或不必要的用户隐私。
5. **防滥用**：服务端限流、请求体大小限制、超时、并发控制、异常处理和成本保护。
6. **安全的 CORS**：只允许所需的来源，不要为了省事对凭据请求开放任意来源。
7. **防止配置泄漏**：公开的健康检查接口只返回必要状态；不得返回密钥、内部环境变量或完整配置。
8. **提示词与输入隔离**：把用户输入视为不可信内容；不能允许用户输入覆盖服务端安全策略或访问后台管理能力。
9. **文件与图片处理**：限制大小和类型；不在日志中长期保留不必要的上传内容；如转发给上游，应明确数据流向。
10. **认证安全**：密码哈希、会话过期、登出、暴力破解防护、用户名唯一约束和权限验证都应在服务端落实。
11. **备份安全**：备份文件不能默认包含明文密钥；下载/恢复操作必须鉴权。
12. **依赖与部署安全**：检查依赖、GitHub Actions 权限、环境变量和部署日志；失败时不能误报成功。

7. 在手机视口下测试登录弹窗、导航、表单、模型选择、会话列表和后台所有主要页面。
8. 至少测试正常请求、上游错误、断网/超时、重复点击、快速连续发送、刷新页面和重新登录。
